# Проверка влияния рекомендаций после внедрения

План B11 по [ТЗ, раздел 10](specs/2026-11-13-recommender-tz.md). Это проект эксперимента, а не отчёт о росте конверсии. В дампе почти нет покупок; исходная конверсия, поток подходящих пользователей и дисперсия активности неизвестны. Параметры ниже — сценарные допущения до измерений на платформе. Запуск требует готового продукта, согласованного протокола и доступа к аналитике; в рамках хакатона эксперимент не проводится.

## Гипотеза и сравнение

Персональный маршрут с объяснениями помогает найти подходящий следующий шаг и повышает долю покупателей курса или подписки «Курс+». Дополнительная цель — увеличить число активных дней пользователя за 28 дней.

Контроль — подборка по совпадению темы из того же каталога, отсортированная по популярности и дате. Тест — персональный рекомендатель. У групп одинаковы интерфейс, число карточек, цены, доступность покупки, таксономия и версия каталога. Внешняя реклама и скидки одинаковы либо учитываются заранее как факторы эксперимента. Сравнение с текущей выдачей платформы возможно отдельным тестом: его нельзя молча смешивать со сравнением с бейзлайном.

Измеряем эффект всего персонального подбора, включая порядок и объяснения, а не отдельного компонента. Если нужен вклад только ранжирования, объяснения и остальные элементы должны быть одинаковы в обеих группах.

## Назначение и анализируемая аудитория

Единица назначения — стабильный пользователь платформы. До вызова конкретного алгоритма первый подходящий запрос страницы рекомендаций создаёт запись назначения: `experiment_id`, псевдонимный `user_id`, вариант, `assigned_at`, версия протокола. Это момент `t0`, одинаково определяемый для контроля и теста. Вариант сохраняется на весь эксперимент и между устройствами после входа.

Распределение: стабильный криптографический хеш идентификатора пользователя и соли конкретного эксперимента. Отдельные диапазоны хеша определяют участие в эксперименте и вариант A/B в соотношении 50/50 внутри участвующего трафика. При пилоте 10% это 5% всей аудитории в A и 5% в B. Число назначений и повторы контролируются сервером, а не JavaScript-сессией.

Подходящая аудитория определяется до назначения: реальные пользователи с доступом к разделу рекомендаций и возможностью совершить новую покупку. Сотрудники, боты и тестовые аккаунты исключаются по заранее зафиксированным признакам. Пользователь с активной подпиской может войти, если ему доступна другая новая покупка; продление по автосписанию не считается новой покупкой. Эти правила одинаковы для групп и не меняются после просмотра результатов.

Основной анализ — intention-to-treat: все назначенные подходящие пользователи, включая тех, у кого карточки не отрисовались, запрос завершился ошибкой или не было клика. Отбор только по фактическому показу может скрыть ошибки тестового варианта. Поэтому отсчёт от первого показа из ТЗ уточняется до первого общего момента назначения перед ранжированием; реальные показы логируются отдельно.

В первом тесте анонимные пользователи без стабильного сопоставления идентификаторов анализируются отдельно и не входят в главную метрику покупки. Нельзя после входа назначать тот же аккаунт повторно в другой вариант. Если сотрудники одной компании существенно влияют друг на друга, перед запуском нужно перейти к назначению по компании и заново рассчитать выборку с учётом кластеризации; пользовательский расчёт ниже для этого случая неприменим.

## Метрики и окна

Для каждого пользователя учитываются события в полуоткрытом окне `[t0, t0 + 28 суток)`. Сутки — 24 часа; активность агрегируется по 28 интервалам `floor((event_ts - t0) / 86400)`, чтобы у каждого были одинаковые окна. События вне окна не используются. Покупка связывается с платёжной системой сервером и дедуплицируется по `order_id`.

До запуска фиксируется единый для всей платформы перечень действий: `platform_visit` (пользователь открыл платформу или перешёл по ней в активной вкладке), `material_open`, `calculator_submit`, `lesson_complete`, `course_enroll`, `new_purchase_confirmed`. Этот нормализованный поток собирается также за пределами страницы рекомендаций и одинаково в A/B. Предзагрузка, автоперезагрузка, фоновые heartbeat и автоматическое продление подписки не создают активного дня. События должны отражать реальное действие, а не число вызовов рекомендателя. При отсутствии общего потока активности показатели активных дней, D7/D28 и CUPED не готовы к измерению.

| Метрика | Расчёт |
|---|---|
| Главная: конверсия в новую покупку | Число назначенных пользователей хотя бы с одной подтверждённой оплатой нового курса или новой подписки в окне / все назначенные пользователи с полностью созревшим окном |
| Активные дни | Для каждого пользователя число 24-часовых интервалов с хотя бы одним содержательным действием на платформе; среднее по всем назначенным, включая нули. Фоновый heartbeat не считается активностью |
| Возврат D7 и D28 | Доля назначенных с содержательным действием в интервалах `[t0+6 суток, t0+7 суток)` и `[t0+27 суток, t0+28 суток)` соответственно |
| CTR карточек | Число уникальных кликнутых показов / число валидных показов карточек. Показ — видимость хотя бы половины карточки не менее секунды; это фиксируемое правило эксперимента |
| Запись на курс | Доля назначенных с новой записью на курс в окне; повтор той же записи не считается новой |
| Завершение курса | Доля назначенных, завершивших хотя бы один курс в окне. Дополнительно — завершения среди начавших, только как диагностическая метрика |

В главную метрику входят все новые покупки назначенного пользователя, а не только покупки после клика по карточке. Так оценивается общий эффект и не игнорируется перераспределение покупок. Связь показа, клика и заказа нужна для диагностики маршрута; она сама по себе не доказывает причинность конкретной карточки. Сумма выручки, возвраты и автопродления отражаются отдельно. Неуспешная оплата покупкой не является; возврат не удаляет факт первоначальной оплаты из главной метрики, но обязательно входит в ограничители.

Классификация `new_course`, `new_subscription`, `auto_renewal` берётся из серверных данных заказа и биллинга, не выводится из клика или цены. В окно входит время фактического успешного платежа `paid_at`, а не время доставки события `received_at`. Если тип покупки или достоверное время неизвестны, результат не готов к расчёту до сверки с биллингом; такие записи нельзя молча считать продлениями или новыми покупками.

Для CTR единица события отличается от единицы рандомизации. Доверительные интервалы считаются с группировкой по пользователю, а не с предположением, что все показы независимы. Метрики завершения и активности могут менять состав пользователей; условные показатели не подменяют ITT.

## Выборка и календарь

Используем нормальное приближение для двух независимых долей, равные группы, двусторонний уровень значимости `alpha=0.05`, мощность `0.8`, без поправки на непрерывность. Число пользователей **на одну группу**:

```text
p̄ = (p0 + p1) / 2
n = ceil((z(1-alpha/2) * sqrt(2*p̄*(1-p̄))
          + z(power) * sqrt(p0*(1-p0) + p1*(1-p1)))² / (p1-p0)²)
```

Это приближённое планирование, не точный расчёт для редких исходов или кластеров. Метод и допущения согласуются с разделом Methods and formulas руководства [Stata: two-sample proportions](https://www.stata.com/manuals/pss-2powertwoproportions.pdf). Перед реальным запуском проверить мощность выбранного итогового теста на актуальной частоте покупок.

Скрипт использует только стандартную библиотеку Python и воспроизводит числа:

```sh
python -m alfarec.eval.sample_size
python -m alfarec.eval.sample_size --baseline 0.01 --relative-lift 0.20 --daily-eligible 10000 --traffic-fraction 0.10
```

| Базовая конверсия | Относительный эффект +10% | +20% | +30% |
|---|---:|---:|---:|
| 0,5% | 327 922 | 85 862 | 39 885 |
| 1% | 163 095 | 42 693 | 19 827 |
| 2% | 80 682 | 21 109 | 9 798 |
| 5% | 31 234 | 8 158 | 3 780 |

В таблице — пользователи на группу при параметрах выше. Например, при `p0=1%`, `p1=1,2%` абсолютная разница составляет **0,2 процентного пункта**, относительная — 20%. Нужно 42 693 пользователя на группу, всего 85 386. Это не прогноз результата рекомендателя.

Пусть `D` — число новых уникальных подходящих пользователей в день до ограничения трафика, `f` — доля участвующего трафика. Набор длится не меньше `max(14, ceil(2*n/(D*f)))` суток. Входящие в `D` пользователи ранее не должны быть назначены в этот эксперимент; DAU с повторными визитами не подходит как поток набора. После закрытия набора ждём ещё 28 суток для последнего участника и предполагаемый лаг данных 2 суток. Итого:

- при условных 10 000 новых подходящих в день и `f=1` — 14 суток набора + 28 наблюдения + 2 лага = **44 суток**;
- при том же потоке и `f=0,1` — 86 + 28 + 2 = **116 суток**.

Пилот на 10% предназначен прежде всего для проверки ошибок и качества логов; покупать статистическую уверенность коротким пилотом нельзя. Если трафика мало, следует увеличить срок или заранее выбрать более крупный минимальный различимый эффект. Нельзя менять главную метрику на CTR после неубедительного результата покупок. Лаг 2 суток — плановое допущение; до запуска его заменяют измеренным SLA платёжных данных.

## A/A и качество данных

До A/B провести A/A: оба варианта используют один и тот же алгоритм. Проверяются постоянство назначения, дедупликация, симметрия потерь событий, сверка оплат с платёжной системой и отсутствие зависимости идентификаторов от устройства. Баланс стадий и исходной активности оценивается только по признакам до назначения. A/A не считается пройденным просто из-за `p > 0.05`.

Сравнение фактического числа назначенных A/B с ожидаемым 50/50 выполняется тестом SRM. Предварительный порог расследования — `p < 0.001` по общему набору; проверки по дням и платформам служат диагностике. Причина разбаланса должна быть выяснена до вывода о пользе: SRM может указывать на ошибки назначения или потери событий, а его игнорирование искажает результат. [Исследование SRM, Microsoft Research](https://www.microsoft.com/en-us/research/publication/diagnosing-sample-ratio-mismatch-in-online-controlled-experiments-a-taxonomy-and-rules-of-thumb-for-practitioners/).

Отдельно сверяются назначения с запросами, показы с успешными ответами и заказы с оплатами. Систематически отсутствующие оплаты нельзя считать нулевыми покупками. При неисправном логировании тест приостанавливается, результат объявляется невалидным; восстановление и новый период фиксируются до повторного анализа.

## Анализ и правило решения

До запуска фиксируются минимальный эффект, размер выборки, длительность, критерии исключения и версия анализа. Главная проверка — двустороннее сравнение двух долей с `alpha=0.05`; сообщаются абсолютная разница в процентных пунктах, относительный эффект, 95% доверительный интервал и численность групп. При редких событиях метод уточняется до запуска, а не выбирается по выгодному p-value.

Результат читается после набора запланированного объёма и созревания 28-дневных окон всех назначенных. Незрелые участники не удаляются для раннего финального отчёта: финальное решение ждёт их наблюдения. Ежедневные панели нужны для качества данных и безопасности, не для остановки при первом значимом улучшении. Если требуется последовательный тест, его границы задаются отдельным протоколом до старта.

Приоритет решения:

1. Нет SRM, потери оплат, нарушения назначения и недопустимого технического ущерба.
2. Нижняя граница интервала эффекта главной метрики выше нуля, а величина эффекта оправдывает расходы на внедрение. MDE из расчёта — параметр мощности, а не автоматический порог доказанной пользы.
3. Активные дни и ограничители не показывают недопустимого ухудшения по заранее выбранным границам. Нет убедительного эффекта — результат «неопределённо», а не «эффекта нет».

Вторичные метрики диагностические; выбор одной из многих удачных метрик не заменяет главную проверку. Для отдельных подтверждающих выводов по нескольким метрикам нужна заранее заданная поправка на множественные сравнения. Разрезы по стадиям и сферам при небольшом числе покупок показываются как исследовательские.

CUPED можно добавить как заранее зафиксированный дополнительный анализ активности: использовать активные дни за 28 суток **до** назначения, с отдельной обработкой новых пользователей без истории. Корректировка не должна использовать события после `t0` и не заменяет рандомизацию. Снижение дисперсии заранее не обещается; основное сравнение покупок остаётся нескорректированным. Основа метода — [Deng и соавторы, CUPED](https://exp-platform.com/cuped/).

Источник признака CUPED — тот же общий поток действий платформы с тем же перечнем событий, но за окно `[t0-28 суток, t0)`. Отсутствие истории отделяется от подтверждённой нулевой активности; ретроспективная подстановка событий из периода теста запрещена.

## Ограничители и остановка

До запуска владелец платформы утверждает границы допустимого ущерба для ошибок API, задержек, возвратов, жалоб и отказов от подписки. Пока эти границы и SLA не определены, эксперимент не готов к запуску. Проектные правила для подготовки пилота:

- Доля платных предложений — не больше одного в первых пяти карточках; нарушение инварианта требует исправления до теста.
- Любая утечка платного содержания или перемешивание историй пользователей — немедленная остановка тестового варианта.
- Ошибки API и p95 задержки сверяются с контрольной группой и согласованным SLA. Техническая деградация не компенсируется ростом CTR.
- Отказы со страницы, «Не то», жалобы, возвраты и отмены подписки сравниваются по назначенным пользователям; изменения состава показов также публикуются.

Остановка из-за вреда фиксируется как остановленный эксперимент, а не как доказательство эффективности или её отсутствия. Во время теста нельзя менять модель, цены или каталог только в одной группе; существенная замена версии требует нового эксперимента либо заранее предусмотренного анализа.

## Логирование и этапы внедрения

| Событие | Минимальные поля |
|---|---|
| Назначение | experiment_id, protocol_version, псевдонимный user_id, variant, assigned_at, eligibility_version |
| Активность всей платформы | event_id, псевдонимный user_id, event_type из фиксированного перечня, occurred_at, received_at, platform; сбор до и во время эксперимента, включая страницы вне рекомендаций |
| Запрос рекомендаций | request_id, user_id, variant, model_version, catalog_version, latency_ms, status |
| Показ карточки | impression_id, request_id, item_id, position, block, reason_codes, displayed_at, visibility rule |
| Клик | event_id, impression_id, item_id, clicked_at |
| Запись и завершение | event_id, user_id, course_id, type, timestamp |
| Оплата и возврат | event_id, псевдонимный user_id, order_id, product_id, type, purchase_kind, paid_at/refunded_at, received_at; статус и тип покупки из биллинга |

Повторная доставка событий не меняет счётчики; записи дедуплицируются по ID. Свободные запросы, личные данные и закрытые тексты не нужны для расчёта эффекта и не передаются во внешние API. Схема эксперимента дополняет продуктовый `Event` из B01: это отдельная аналитическая интеграция, не уже работающий endpoint.

Порядок внедрения: воспроизводимая офлайн-оценка B06 → проверка журналов и A/A → необязательный interleaving для чувствительной диагностики предпочтения порядка → технический пилот на 10% → A/B с заранее рассчитанным объёмом → постепенная раскатка с сохранением контрольной группы. Interleaving не оценивает 28-дневную покупку; его пользователи и данные не смешиваются с последующим A/B без отдельного протокола. Пилот может входить в основной анализ только при неизменных назначении, версиях и заранее зафиксированном плане; иначе он считается отдельным этапом.
