# B06: ручная разметка релевантности

Этот документ описывает исходный TF-IDF-пакет. Финальная оценка ML и выбранные веса — [итог B06](../reports/b06_final.md). Статусы ниже относятся к историческому этапу; новые ответы не требуются.

Статус: **пул и форма готовы, ожидаются оценки двух участников**. Это главная проверка [ТЗ, раздел 9](specs/2026-11-13-recommender-tz.md): nDCG@10, Precision@5 и MRR нашей системы против бейзлайна на 36 тестовых профилях. Шкала и правила — [инструкция разметки](labeling.md).

## Действия участников

1. Договориться о кодах A и B. Каждый открывает в обычном браузере файл [`artifacts/judgments/form.html`](../artifacts/judgments/form.html): он самодостаточный, сервер и сеть не нужны. Не размещать файл на публичном хостинге.
2. Выбрать свой код вверху формы. Появятся назначенные профили: у A — 399 пар, у B — 361, из них пять профилей (P01, P16, P26, P30, P34) общие. Оценки общих профилей не обсуждать до скачивания своих файлов: по ним считается каппа Коэна.
3. Для каждой карточки поставить 2, 1, 0 или «?» по инструкции. У «?» обязательно пояснение. Ответы сохраняются в этом браузере между открытиями, если хранилище не отключено; надёжная копия — только скачанный файл.
4. Подтвердить самостоятельность и нажать «Скачать мои оценки · JSON». Передать координатору `b06-judgments-A.json` и `b06-judgments-B.json`.
5. Координатор сводит файлы:

```sh
python -m alfarec.eval.judgments merge b06-judgments-A.json b06-judgments-B.json
python -m alfarec.eval
```

Первая команда проверяет файлы и пишет `alfarec/eval/judgments.csv` с исходными оценками и отчёт о согласованности `reports/judgments_agreement.md` с каппой и списком расхождений. Вторая добавляет метрики разметки в [отчёт оценки](../reports/eval.md).

6. Участники обсуждают расхождения общих профилей. Итог записывается в `alfarec/eval/judgments_resolved.csv` (`profile_id,item_id,grade`); до этого в метриках берётся меньшая оценка. Исходные оценки не редактируются.

## Как собран пул

`python -m alfarec.eval.judgments pool` строит топ-10 (маршрут, затем «Ещё по теме») для каждого профиля в пяти вариантах: наша система, бейзлайн, без стадии и уровня, без истории, без переранжирования. В пул входят только топ-10 нашей системы и бейзлайна — 666 пар. Это осознанное отступление от шага 2 протокола в [инструкции](labeling.md), где пул включает все варианты: полный пул (809 пар) не помещался во время команды до сдачи. Списки абляций строятся и хранятся, но их метрики в отчёте помечены «не измерены»: считать их по частично оценённому пулу было бы смещённо. Карточки перемешаны с фиксированным зерном; источник, позиция, score и ожидаемое поведение в форму не попадают. Легенда профиля показывается как пояснение сценария: оцениваются только потребности из полей профиля и истории.

История профилей задана селекторами (задача, тип материала, уровень). Она разрешается в материал с самой высокой популярностью среди подходящих по исходной разметке; если подходящих нет — ближайший по тексту задачи. Выбор проверен вручную: для P24 текстовый поиск дал «Сумма прописью онлайн» вместо калькулятора финансирования, поэтому выбран «Калькулятор процентов». Для P26 нет начального курса по налогам; взят «Наличка: как использовать, чтобы не нарушить 115-ФЗ». Разметчики видят историю в форме.

Пул фиксирует SHA-256 упорядоченных списков всех вариантов, каталога, профилей, таксономии, переходов между курсами, индекса и инструкции. `python -m alfarec.eval.judgments pool --check` проверяет, что пул соответствует текущему коду и данным; после изменения ранжирования оценки нужно собирать заново по новому пулу.

## Метрики

- nDCG@10 с выигрышем `2^оценка − 1`; идеальный порядок — по всем оценённым карточкам профиля.
- Precision@5 и MRR считают релевантной оценку 2 («прямо полезно»).
- «?» и неоценённые карточки пропускаются; их число показывается отдельно.
- Основное сравнение — `holdout` (14 профилей); `tune` (22) — для подбора весов и показывается отдельно.
