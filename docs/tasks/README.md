## Незавершённая работа и передача

Обязательные остатки фиксируются в соответствующей карточке [CORE.md](CORE.md), а не только в описании PR или локальной заметке. У частично выполненной задачи остаётся `in_progress`, `review` или `blocked`: слитый код либо готовый отдельный этап не закрывает всю карточку. `POLISH.md` предназначен для мелких замечаний, не нарушающих приёмку.

Для продолжения в карточке должны быть: что уже проверено; что ещё не сделано; точный недостающий вход; кто этот вход готовит; кто продолжает работу; событие разблокировки; критерий завершения и ссылка на доказательства с SHA. Создание PR, наличие файла и полная приёмка результата отмечаются отдельно.

Когда вход готов, его исполнитель обновляет передачу в карточке: версия, согласованные пути, хеши и результат проверки. Получатель проверяет совместимость, закрепление задачи и затем меняет статус на `in_progress`. Закрытый исходный файл не коммитится; в карточке остаются его назначение и версия, без секретов и содержимого.

Текущие незавершённые части описаны в карточках B03 (реальная калибровка разметки) и B04 (передача данных, выбор модели, ML-метки, граф и CPU-приёмка). Локальная `.work/STATE.md` помогает восстановить рабочую сессию и не заменяет эти общие записи.

## Как выбираем следующую задачу

1. Задача имеет понятные границы, входы, результат и критерии приёмки; существенные решения согласованы.
2. Все её обязательные зависимости приняты по критериям соответствующих карточек. «Есть код» или «открыт PR» не равно завершённой зависимости.
3. Задача свободна: проверены текущий код и PR; владелец закреплён ранним черновиком PR.
4. Из доступных задач сначала берём ту, которая открывает критический путь либо снимает самый существенный риск; затем учитываем приоритет и срок.
5. Учитываем изменения в общих файлах и контрактах. Независимость по функции не гарантирует отсутствия конфликта редактирования.

Приоритет и зависимость — разные вещи: задача с высоким приоритетом может ждать входов; свободный участник в это время берёт другую готовую задачу. При блокировке записать недостающий вход и точное условие разблокировки.

Статусы: `todo` — не выполнены зависимости или не проработана карточка; `ready` — можно брать; `in_progress` — закреплена и выполняется; `review` — ждёт приёмки; `blocked` — возник конкретный блокер; `done` — принята, со ссылкой на слитый PR и проверки.

## Где лежат карточки

После согласования спецификации карточки заводятся в двух файлах:

- `docs/tasks/CORE.md` — обязательное ядро, ID `B00`, `B01`, …;
- `docs/tasks/IMPROVEMENTS.md` — улучшения, ID `E01`, `E02`, …

Требования — в `docs/hackathon/REQUIREMENTS.md`, ID `F01` (функциональные), `S01` (сдача), `O01` (опциональные), `U01` (удобство).

Как только появляется любой из трёх файлов, `scripts/check.ps1` требует все три и проверяет граф целиком. Формат, который он ожидает:

- в CORE.md и IMPROVEMENTS.md — таблица `| ID | Задача | Зависит от | Требования | …` и для каждой строки раздел `## B01. Название` с карточкой;
- ядро не зависит от улучшений, циклов зависимостей нет;
- в REQUIREMENTS.md — таблица определений `| ID | Требование | Уровень | Как проверяем |` и таблица покрытия `| Требования | Задачи |`; каждое требование покрыто хотя бы одной задачей.

## Формат карточки

```text
ID и название:
Приоритет:
Связанные требования:
Цель и наблюдаемый результат:
Зависимости (ID и нужный принятый результат):
Входы и существующие контракты:
Границы работы и явные исключения:
Выходные файлы / интерфейсы / артефакты:
Критерии приёмки:
Проверки и доказательства:
Риски и условие разблокировки:
Статус:
Владелец:
Ветка / PR:
```

Карточка должна позволять исполнителю работать без восстановления всей истории обсуждения. Задачи делятся по проверяемому результату.

Мелкие доработки, не блокирующие приёмку, — в [`POLISH.md`](POLISH.md).
