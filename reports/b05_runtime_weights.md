# B05: загрузка весов в API

Основа `4d6a24b`, продолжение принятой B04 из #34. API использует dense-поиск,
ML-метки и семантический граф. Добавлено чтение `artifacts/weights.json` при
старте с валидацией схемы, каталога, признаков и диапазона 0–1000.
`WEIGHTS_PATH` задаёт локальный файл; `weights_path=None` отключает загрузку
при офлайн-сравнении. Частичные overrides применяются после сохранённых весов.

Проверка через FastAPI TestClient, Windows, CPU, локальная E5-small
`614241f622f53c4eeff9890bdc4f31cfecc418b3`, каталог 1497:

| Режим | Профилей | Максимальная HTTP-задержка | Контрольные веса применены |
|---|---|---|---|
| dense | 36 | 102 мс | да |
| TF-IDF | 36 | 60 мс | да |

История каждого сценария фиксируется одинаково по исходной разметке каталога,
а не заново по ML-предсказаниям. Проверены отсутствие дублей между блоками,
исключение complete/known/dislike, квота платного в первых пяти more и уточнение
во всех предусмотренных сценариях. Health сообщает фактический режим.

Контрольный файл удваивает все веса и меняет score реальной HTTP-выдачи.
Это тест подключения, а не подобранные веса: файл не публикуется как итог B06.
Тесты ошибок покрывают отсутствие явно указанного файла, повреждённый JSON,
чужой каталог, NaN, неизвестный признак, bool и числа с переполнением.
Во всех случаях сервис отвечает через baseline с degraded.

Полная B05 остаётся review до выбора и приёмки весов B06. Релевантность,
конверсия и запуск на второй физической машине этим отчётом не подтверждаются.

Большой прогон B06 выявил повторный расчёт сходств внутри MMR при limit=50.
Локальный накопленный максимум исключает повторную обработку тех же пар.
Полные ответы прежней и ускоренной реализации побайтно совпадают после
сериализации JSON на 36 профилях каждого режима, включая фиксированные истории.
Контрольный профиль с историей и limit=50 после исправления: dense 275 мс,
TF-IDF 67 мс. Отдельный тест проверяет, что каждая пара обрабатывается один раз,
включая переданный prefix; квоты и порядок выбора сохраняются.
